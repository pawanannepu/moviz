## Summary
This change swaps the `/home` placeholder for the personalized feed from spec 0008. The guarded page streams the header, the `h1`, the `noscript` line and a `LoadingState` first. A server `Feed` makes one `loadFeedBatch` call. A client `FeedList` owns the picks, the dedupe, the live region and the new `LoadMoreBar`, and `loadMoreAction` is the only new Server Action. The code is small and follows the spec closely: typed results, Zod, session-only user id, the `retry` (not `reset`) boundary, and a well-designed focus and announcement model. Unit and component tests are thorough. The one real problem is privacy. An unexpected recommender failure is rethrown with Drizzle's query parameters in its message, which can include the user's liked movie ids and their weights, and Next.js logs it on the server. That breaks AC-14. The rest is small: focus visibility, browser coverage gaps and copy drift.

## Major

### 🟠 Unexpected recommender errors reach the server log with rating data in the message, `src/feed/load-feed-batch.ts:25`
**Problem**: `loadFeedBatch` handles `db_unavailable` and `invalid_input`, but any other error from `recommendMovies` propagates unchanged. `recommendMovies` rethrows everything that `toDbFailure` does not map (`src/recommend/recommend-movies.ts:128`). Drizzle 0.45.4 wraps a failing query in `DrizzleQueryError`, whose message is `Failed query: <sql>\nparams: <params>` (`node_modules/drizzle-orm/errors.js:12`). For the scoring query those params are the user id, the anchor movie id array, the anchor weight array (derived from the user's scores) and the `shown` id array (`src/recommend/score-candidates.ts:57-82`). The error escapes both feed edges. From `Feed` (`src/feed/feed.tsx:16`) it goes to `home/error.tsx`, and from `loadMoreAction` (`src/feed/actions.ts:42`) it becomes a rejected action. Next.js logs both on the server with the full message and `cause` chain. Some of these errors are not connection failures: a statement timeout or cancel (`57014`), a planner or SQL bug, or a vector dimension mismatch after an embedding model change.
**Why it matters**: AC-14 says no log line or thrown message holds a rating, a score, a title or a movie id. Root `AGENTS.md` says ratings content never goes to logs. On Vercel those server logs keep which movies a user liked, with their weights, and that data lands with whoever can read the logs. The leak is latent, because the happy path and `db_unavailable` are clean. That is why the console spy tests and the manual log check in `verify.md` did not catch it.
**Suggested fix**: Clean the error at the one choke point, so neither edge can leak. The best place is the `catch` in `recommendMovies`: rethrow a new `Error` with a fixed message and only the SQLSTATE code (for example "recommender query failed (57014)"), with no `cause`, because Next.js prints causes too. Keep the original only in a debugger, never in a log. If you would rather keep spec 0007 untouched, wrap the call in `loadFeedBatch` the same way. Add a test where the recommender throws an error whose message and `cause` hold ids, and assert the error leaving `loadFeedBatch` or `loadMoreAction` holds neither.

## Minor

### 🟡 A programmatic focus move after a pointer press shows no focus ring, `src/ui/load-more-bar.tsx:60`
**Problem**: Runtime verification found no visible ring on the Sign in link after a lost session. This is most likely the browser's `:focus-visible` heuristic, not a CSS gap. The global rule (`src/app/globals.css:96`) styles only `:focus-visible`. When the Load more button unmounts and `linkRef.current.focus()` runs after a mouse or touch press, Chromium does not match `:focus-visible`. After a keyboard Enter it should. The same applies to the done line (`doneRef`). No test asserts the ring on the keyboard path, so I can't confirm that path from code alone.
**Why it matters**: WCAG 2.4.7 holds as long as the keyboard path shows the ring. A pointer or magnifier user whose focus jumped to a new control still gets no visual cue where focus went, and the spec's goal for AC-10 ("never dropped to the page body") is about knowing where you are.
**Suggested fix**: Re-run the lost session path with Tab and Enter only, and assert the link matches `:focus-visible` (for example `expect(link).toHaveCSS("outline-style", "solid")` or `link.evaluate(el => el.matches(":focus-visible"))`). If you want a ring after pointer presses too, pass `focus({ focusVisible: true })` where the browser supports it, and accept the default elsewhere.

### 🟡 `home/error.tsx` retry has no double press guard, `src/app/(protected)/home/error.tsx:27`
**Problem**: The in page `FeedLoadError` ignores presses while `router.refresh()` runs and announces "Loading your picks". The page level boundary passes `retry` straight to `onRetry`. Each press fetches the page again, which reruns `requireUser`, `getProfile` and one full recommender call of 2 to 3 s.
**Why it matters**: A user facing a slow or failing page is the one most likely to press Try again repeatedly. That multiplies the most expensive query exactly when the system is struggling, and it breaks the spirit of AC-13's one call per load. Screen reader users also get no feedback that the retry is running.
**Suggested fix**: Use the `FeedLoadError` pattern: run `retry` inside `startTransition`, ignore presses while pending, and render the same polite status. Alternatively, check whether Next 16.4's `retry` already dedupes, and note it in a comment if so.

### 🟡 Browser coverage misses several AC-15 and AC-10 states, `e2e/auth/feed.spec.ts:158`
**Problem**: AC-15 asks for a browser axe scan in the loaded, thin, pending, error and done states. The spec has loaded, thin, pending and error. Done is reached only by chance in the keyboard test (line 179), and that test does not assert it. Other gaps:
- There is no browser test for `session_ended`. The spec's critical scenarios call for a mocked `unauthenticated` result with focus on the link.
- The reduced motion test (line 144) checks only overflow, not that nothing animates.
- AC-14 has no browser or server log check: the `verify.md` step is manual.

The component tests (`feed-list.test.tsx`) cover these states in happy-dom, but without real layout or focus visibility.
**Why it matters**: The done and lost session states are where focus moves, and that is where the focus ring question above lives. Contrast and focus visibility can only be measured in a browser.
**Suggested fix**: Add a done-state test by routing the action to a fulfilled response with `done: true`, or a catalog-independent fixture. Add a lost session test (clear cookies, then press with the keyboard) that asserts focus, `:focus-visible` and an axe scan. In the reduced motion test, assert the reason reveal's computed `animation-name` or `transition-duration`.

## Strengths
- The focus and announcement model is careful and correct. One button element covers idle, pending and error, so focus never leaves it. Focus moves only on a change out of `pending`, so a first batch that is already done never steals focus. The live region is cleared before each call, so the same message is read twice.
- The boundaries are clean. The user id comes only from `getUserForAction()`, unknown keys are stripped by Zod, the session is checked before the input, and failures are typed results. `done` counts distinct `shown` ids, so the client can never be pushed past the 500 cap that Zod enforces.
- `error.tsx` correctly uses Next 16.4's `retry` (confirmed against `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/error.md`). The in page retry runs `router.refresh()` only where `FeedList` is not mounted, as the spec intends.
- The tests are strong. They cover the 500 boundary on both sides, the distinct id count, the dedupe, singular and plural announcements, the pending double press, rejection versus typed errors, the session-before-input order, the one call per load and per press, the `noscript` placement and component-level axe on every state.
